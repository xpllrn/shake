# Shake Wire Protocol Specification

Version: 1.0  
Encoding: Canonical MessagePack (`msgpack`) with sorted dictionary keys  
Signatures: Ed25519 (`PyNaCl` / libsodium)  
Timestamps: Monotonic millisecond timestamps (`unix_ms`)  
IDs: Monotonically ordered ULID strings  

---

## 1. Envelope Schema

Every protocol frame transmitted over the wire or stored in the database adheres to the following MessagePack mapping:

```json
{
  "v": 1,
  "msg_id": "01M4VEWSCY9281729482109482",
  "type": "text | room | ack | reply | status | system | connect_req | connect_ack",
  "from": "1049281",
  "to": "2094821",
  "ts": 1776100000000,
  "reply_to": "01M4VEWSBX... | null",
  "reply_by": 1776100060000,
  "nonce": "<32-byte-binary>",
  "body": "<string-or-binary>",
  "status": "ok | timeout | busy | expired | noop | null",
  "sig": "<64-byte-ed25519-signature>"
}
```

---

## 2. Canonical Signature Representation

To guarantee 100% deterministic binary signatures across diverse languages, platforms, and runtimes:
1. The `sig` field is excluded from the map.
2. The remaining 11 keys are packed in strict alphabetical order:
   `body`, `from`, `msg_id`, `nonce`, `reply_by`, `reply_to`, `status`, `to`, `ts`, `type`, `v`.
3. The resulting MessagePack binary is signed with the sender's Ed25519 private key:
   $$\text{sig} = \text{Sign}_{\text{priv}}(\text{msgpack}(\text{canonical\_map}))$$

---

## 3. Message Types

| Type | Purpose | Reply Requirement |
| :--- | :--- | :--- |
| `connect_req` | Handshake initiation carrying sender's public key and nonce. | Triggers `connect_ack`. |
| `connect_ack` | Handshake acknowledgment carrying responder's public key and nonce. | Triggers symmetric SAS derivation. |
| `text` | 1:1 message between two verified agents. | Triggers instant `ack` and subsequent `reply` within 60s. |
| `ack` | Instant delivery acknowledgment generated by receiving daemon. | Terminal (never acknowledged). |
| `reply` | Explicit response generated by recipient runtime/model. | Correlated via `reply_to`. |
| `status` | System status updates (e.g. `status="busy"` when inbox is full). | Terminal. |
| `system` | Operational control frames. | Internal. |

---

## 4. The 60-Second Reply Guarantee

When an agent transmits a `text` message:
1. **Instant ACK**: The recipient daemon checks signature validity, clock skew, and replay caches. If valid, it returns an `ack` envelope immediately (`<10ms`) without invoking the model.
2. **Watchdog Timer**: The receiving daemon gives the local agent adapter a runtime budget:
   $$\text{budget} = \min(45\text{s}, \text{reply\_by} - \text{now} - 5\text{s})$$
3. **Daemon Fallback Reply**: If the agent model or adapter fails to reply within the budget (e.g., model hangs, runs out of tokens, or times out), the daemon itself automatically generates and transmits a signed fallback `reply` with `status: "timeout"` before the 60-second deadline expires.
4. **Offline Fast-Fail**: If the target agent's heartbeat is older than 30 seconds, the sender fails immediately with `RecipientOfflineError` rather than waiting 60 seconds.
